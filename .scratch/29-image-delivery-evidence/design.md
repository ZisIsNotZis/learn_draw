## Supported request and response seams

Pi SDK `docs/sdk.md` describes its `createAgentSession`/`DefaultResourceLoader` extension model and `session.dispose()` cancellation. Installed `dist/core/sdk.js` wires `before_provider_request` to pi-ai `onPayload`, `after_provider_response` to the response status/header event, and `provider_stream_event` to parsed provider events (`sdk.js:225-251, 274-276`). Extension event types define the first as arbitrary payload before request, response event as status/headers, and stream event as parsed structured data (`dist/core/extensions/types.d.ts:679-705,1179-1182`). These events can establish transformed request content, response metadata, and a provider response ID; they are not the original HTTP bytes or a network/provider receipt. The installed `provider-payload.ts` example writes the entire prompt/request payload and headers to a log; it is unsafe for this task and must not be used as written. `debug-provider.ts` also persists raw parsed events; do not enable it.

Active-runtime source in pi-ai 0.79.10 shows GitHub Copilot handling inside the generic OpenAI Responses adapter, not a separate `github-copilot.js` provider factory: `dist/providers/openai-responses.js:148-155` adds Copilot headers for provider ID `github-copilot`; shared Responses message conversion encodes image blocks as data URIs (see `dist/providers/openai-responses-shared.js`). It invokes `onPayload` before request and `onResponse` after HTTP response (`openai-responses.js:68-108`), parses provider events into a normalized AssistantMessage with `responseId` and emits `done` (`openai-responses-shared.js` and `openai-responses.js:98-120`). It does not forward custom `fetch`; see `issues/05-active-runtime-stream-repair.md`. `onPayload` proves only the transformed structured payload, not serialized bytes or network delivery.

Historical assumption (superseded by active-runtime check): an earlier runtime's `StreamOptions` was believed to expose `fetch?: typeof globalThis.fetch`, making custom-provider fetch observation seem supported. Active pi-ai 0.79.10 `dist/types.d.ts:34-84,151-156` has no `fetch` option; `dist/providers/openai-responses.js:145-179` constructs the OpenAI client without a fetch override. Its declared `onPayload`/`onResponse` hooks observe pre-send payload and HTTP response metadata but not the serialized request body at fetch. Thus the described actual-Request/custom-fetch transport seam is unavailable in the active runtime. See `issues/05-active-runtime-stream-repair.md`; do not treat subsequent historical proposed launch instructions as executable.

Extension registration is generally supported, but no built-in `githubCopilotProvider()` export/source exists in the active pi-ai 0.79.10 or coding-agent dist; the installed active implementation is the generic `streamOpenAIResponses`/`streamSimpleOpenAIResponses` adapter exported at `@earendil-works/pi-ai/openai-responses`, registered for the `openai-responses` API. The former proposed provider-wrapper/fetch-observer design is not executable against active exports and options. Do not infer an export from historical design text; see `issues/05-active-runtime-stream-repair.md`.
